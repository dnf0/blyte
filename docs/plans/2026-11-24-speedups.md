# Fewer processes and shorter waits in normal use

2026-11-24. The test-speed work (#407, #409) was not allowed to change product code and reported
four product costs instead. A read-only research run (RS1) listed every process each one starts.
This plan removes the ones that can go without changing what a user sees.

What RS1 found, against `origin/main` at 45c1d08:

- `blyte clean` asks git the same kind of question once per run, worktree or branch (ref tips,
  trees, "is this merged"), and rebuilds its lookup context per session worktree.
- Combining a request's runs starts about 24 processes for two runs. Several ask for the git
  common directory again, or resolve a ref that was resolved a few lines earlier.
- `exec_command_cancellable` in `crates/blyte-agent/src/shell.rs` waits for its child with a fixed
  50 ms sleep, so every `LocalShell` command takes at least 50 ms. `run_command_bounded` in
  `crates/blyte-agent/src/tools.rs` already backs off from 1 ms to 50 ms.
- `SessionFs::write` no longer starts `base64` (removed earlier). It and `Session::run` still start
  `mkdir -p` on every call, when the directory nearly always exists. `SessionFs` is used for
  container runs; local runs use `LocalFs`.

Not in this plan, because RS1 showed a risk of changed behaviour: one `git branch -D` for all
branches (changes output order and partial failure), one `git cherry-pick` for several commits
(loses which commit failed), skipping the clean-tree check before the check on a combined branch,
reading files or resolving paths with shell builtins instead of `cat` and `readlink -f`, and
parsing a worktree's `.git` file by hand.

## Rules for every task

- What a user sees does not change: the same output lines in the same order, the same error
  messages, the same exit codes, the same files and refs afterwards. No new flag, `blyte.toml` key
  or environment variable.
- Every existing test and assertion stays and passes unmodified, except where a task says a named
  test may change. Do not delete, `#[ignore]` or weaken a test.
- No fallbacks: when a batched lookup does not contain an answer (a base that is a raw commit or a
  tag, a detached worktree), ask git for that one answer as the code does today, and fail as it
  does today when git fails. Never treat "not in the table" as "not merged", "merged" or empty.
- Change only the files the task names. If the cause is elsewhere, leave it and report it.
- Not resumable work: none of these commands runs for more than seconds.
- Report: the process count before and after for the task's test, and anything left alone and why.
- Full check before the commit:
  `cargo fmt --all --check && cargo clippy --all-targets -- -D warnings && cargo test --workspace --all-targets`

### Task PS1: shell commands return as soon as they finish

**Depends on:** none. **Siblings (not in this worktree):** PS2 changes `clean.rs`; PS3 changes
`combine.rs`. Do not touch either.

**Files:** `crates/blyte-agent/src/shell.rs`, `crates/blyte-agent/src/tools.rs`,
`crates/blyte-agent/src/fs.rs`, and one new test file
`crates/blyte-agent/tests/test_poll_backoff.rs`.

**What to build**

1. In `crates/blyte-agent/src/tools.rs`, `run_command_bounded` sleeps `poll.min(remaining)` and
   then sets `poll = (poll * 2).min(Duration::from_millis(50))`, starting from 1 ms. Move that
   arithmetic into one public function in `shell.rs`:

   ```rust
   /// How long to sleep before checking a child again, and the interval to use next time:
   /// 1 ms doubling to 50 ms, never longer than the time left before the deadline.
   pub fn poll_backoff(current: Duration, remaining: Duration) -> (Duration, Duration)
   ```

   It returns `(current.min(remaining), (current * 2).min(Duration::from_millis(50)))`. Add
   `pub const POLL_START: Duration = Duration::from_millis(1);`. `run_command_bounded` calls it;
   its behaviour is unchanged.
2. In `exec_command_cancellable` (`shell.rs`, the wait loop that today has
   `None => std::thread::sleep(Duration::from_millis(50))`), use the same function: start at
   `POLL_START`, sleep the first value, keep the second. `remaining` is
   `deadline.saturating_duration_since(Instant::now())`. Nothing else in the loop changes: output
   is still drained on the two threads and joined after the loop, the process group is still killed
   and reaped on timeout and on cancel, in the same order.
3. In `Session::run` (`shell.rs`, the line containing `mkdir -p {qt} 2>/dev/null;`), start `mkdir`
   only when the directory is missing: `[ -d {qt} ] || mkdir -p {qt} 2>/dev/null;`.
4. In `SessionFs::write` (`fs.rs`, `format!("mkdir -p -- {} && ", sh_quote(&dir))`), the same:
   `{{ [ -d {d} ] || mkdir -p -- {d}; }} && ` so that a failed `mkdir` still fails the write.

Do not change `SessionFs::read`, `SessionFs::canonicalize` or `ContainerFs`.

**Tests** (`crates/blyte-agent/tests/test_poll_backoff.rs`)

- `backoff_doubles_from_one_millisecond_to_fifty`: starting at `POLL_START` with a remaining time
  of 10 s, the sleeps are 1, 2, 4, 8, 16, 32, 50, 50 ms.
- `backoff_never_sleeps_past_the_deadline`: `poll_backoff(50 ms, 7 ms)` sleeps 7 ms;
  `poll_backoff(50 ms, 0)` sleeps 0.
- `session_write_creates_a_missing_directory_and_reuses_an_existing_one`: with
  `SessionFs::local` in a temporary directory, write `a/b/one.txt` (directories missing), then
  `a/b/two.txt` (directory present), then overwrite `a/b/one.txt`; read all back and compare.
- `session_write_fails_when_the_directory_cannot_be_made`: create a regular file `blocker`, then
  write `blocker/x.txt`; the write returns `Err`.

If `test_persistent_shell.rs` or `test_session_self_heal.rs` match the old command text, say so in
the report and change only the matched text.

Run: `cargo test -p blyte-agent --test test_poll_backoff`

**Commit message:** `perf(agent): poll a finished command from 1 ms, and start mkdir only for a missing directory`

### Task PS2: `blyte clean` asks git once for what it asked per run

**Depends on:** none. **Siblings (not in this worktree):** PS1 changes `crates/blyte-agent`; PS3
changes `combine.rs` and may change `config.rs`. Do not touch either.

**Files:** `crates/blyte-cli/src/clean.rs` and one new test file
`crates/blyte-cli/tests/test_clean_git_calls.rs`.

**What to build**

1. One ref table on `CleanContext`, filled by a single
   `git for-each-ref --format=%(refname)%09%(objectname)%09%(symref)%09%(tree) refs/heads refs/remotes/origin`.
   Answer from it: the `wip/` branch tips, the default branch and `origin`'s default, tree hashes
   (`git_tree_sha`), base targets (`resolve_base_targets`) and branch tips (`get_branch_tip`). A
   name not in the table (a raw commit, a tag, anything else) goes to git exactly as today.
2. One `git for-each-ref --merged=<target> --format=%(refname:short) refs/heads` per default target
   (the default branch, and `origin`'s default when it exists) to fill the ancestor cache for every
   branch at once. A detached worktree's commit is not a branch: it still uses
   `git merge-base --is-ancestor` as today.
3. Build `CleanContext`, the linked-worktree check and the parsed `git worktree list` once per
   `clean`, and use them for `.wt/` runs, session worktrees and the report of other worktrees.
   `is_branch_merged` must not build a new context per worktree. Worktrees removed earlier in the
   same `clean` must still be left out of the later steps (they are filtered by path existence
   today; keep that).
4. Skip `get_wip_branches_containing` when every start record has a `base`.
5. Run `git worktree prune` once, after the removal loops, instead of inside them.
6. In `find_repo_root`, one `git rev-parse --path-format=absolute --show-toplevel --git-dir --git-common-dir`
   instead of two calls plus `config::main_checkout`'s third. Do not change `config.rs`: read the
   common directory from the call you already make.

Leave as they are: `git cherry`, `git merge-tree`, the per-worktree `git status`,
`git worktree remove`, the per-branch `git branch -D` and its output line directly after the
`removed` line, and `is_worktree_idle`.

**Tests** (`crates/blyte-cli/tests/test_clean_git_calls.rs`)

Count git processes with a wrapper: a directory first on `PATH` holding an executable `git` script
that appends its arguments as one line to a log file named by `BLYTE_TEST_GIT_LOG` and then
`exec`s the real git (its absolute path found once with `which git` in the test). Run `blyte` as a
child with `BLYTE_NO_UPDATE_CHECK=1`, its own `HOME` and state directory, as the other clean tests
do. Turn off background maintenance in fixture commits (`git -c maintenance.auto=false -c gc.auto=0 commit`).

A helper builds a repository with `k` runs under `.wt/`, each with a start record whose `base` is
`main`, a `wip/<id>` branch with one commit not merged anywhere, and a linked worktree.

- `lookups_do_not_grow_with_the_number_of_runs`: run `blyte clean` with k = 2 and with k = 8
  (nothing is removed in either). The number of logged calls whose first argument is `rev-parse`,
  `for-each-ref`, `show-ref`, `symbolic-ref` or `merge-base` is the same for both.
- `total_calls_grow_by_at_most_three_per_kept_run`: `(calls(8) - calls(2)) / 6 <= 3`. Print both
  totals with `eprintln!`. Before changing `clean.rs`, run this test on the unchanged code and put
  the numbers in the report.
- `merged_runs_are_still_removed_and_reported_in_order`: k = 3, two of them merged into `main`
  with `git merge --no-ff`; the output has, for each merged run, its `removed .wt/<id>` line
  followed directly by its `deleted branch wip/<id>` line, the third run is kept, and
  `git worktree list` no longer shows the two.
- `a_base_that_is_a_commit_still_resolves`: one run whose start record's `base` is the full commit
  hash of `main`, merged; it is removed.

Run: `cargo test -p blyte --test test_clean_git_calls`, then every `test_clean*` file.

**Commit message:** `perf(clean): read refs and merged branches once instead of once per run`

### Task PS3: combining runs stops asking git the same thing twice

**Depends on:** none. **Siblings (not in this worktree):** PS1 changes `crates/blyte-agent`; PS2
changes `clean.rs`. Do not touch either.

**Files:** `crates/blyte-cli/src/combine.rs`, `crates/blyte-cli/src/config.rs` only for item 2, and
one new test file `crates/blyte-cli/tests/test_combine_git_calls.rs`.

**What to build**

1. Find the git common directory (and the main checkout) once at the start of `run_combine_inner`
   and pass it to `ensure_wt_excluded`, `setup` and `passed_trees`, instead of each asking git.
2. `config::load` asks git for the main checkout only to resolve `dispatch.allow_read`. When
   `allow_read` is empty, do not ask. Nothing else in `config.rs` changes.
3. Resolve the starting refs in one git call: every run's base, every run's `refs/heads/<branch>`,
   and `refs/heads/blyte/<request>`. A ref that does not resolve produces the same error text as

   and `rev-parse` again.
5. `git worktree add -B <branch>` instead of `git branch -D` followed by `git worktree add -b`.
6. Run `git cherry-pick --abort` only when `CHERRY_PICK_HEAD` exists in the worktree's git
   directory, and `git worktree prune` only when a worktree is rebuilt or an error path needs it.
7. Do not run `git rev-parse HEAD` after the last run when its value is not used.
8. One `git log --reverse --format=%H%x20%T <group_base>..HEAD` for the combined commits and the
   final tree, instead of a commit listing plus `rev-parse HEAD^{tree}`.

Leave as they are: one `git cherry-pick -x` per commit, the clean-tree check before the check on
the combined branch (`git status --porcelain`), the check command itself, and the records written.

## Test files side by side

`cargo test` runs one test file's binary at a time. Measured on `main` at 45c1d08 on a machine
that was also running three dispatches (2026-11-24): the 251 test binaries took 336 s one at a
time, 108 s four at a time and 107 s eight at a time, with every binary passing at four. The two
failures seen at one and eight were `test_clean_followups` (a 3 s timing guard on `blyte clean`,
which Task PS2 makes faster) and, once, `test_build_stamp` while another build was running.

A first attempt ran the binaries without the `[env]` table of `.cargo/config.toml`. The tests then
loaded the developer's key file and made real requests. The script below must set that table.

### Task PS4: run test binaries four at a time

**Depends on:** none. **Siblings (not in this worktree):** PS1 changes `crates/blyte-agent/src`;
PS2 changes `clean.rs`; PS3 changes `combine.rs` and `config.rs`. Do not touch them.

**Files:** new `scripts/test-parallel.py`; `scripts/test-changed.py`; `.github/workflows/ci.yml`
(the one `cargo test --workspace --all-targets` step); new
`crates/blyte-cli/tests/test_test_parallel_script.rs`;
`crates/blyte-cli/tests/test_test_changed_script.rs` only where it matches the command text that
changes; `CLAUDE.md` and `CONTRIBUTING.md` only where they state the test command.

**What to build**

`scripts/test-parallel.py [--jobs N] [--root DIR] [--executables-from FILE] -- <cargo test arguments>`

1. `--root` is the workspace root (default: the parent of the script's directory).
2. Build first, with output shown: `cargo test <arguments> --no-run` in the root. If it fails,
   exit with its code. Then run the same command with `--message-format=json` and take every
   `compiler-artifact` message that has an `executable` and whose `profile.test` is true: the
   executable, and the directory of its `manifest_path`.
3. `--executables-from FILE` skips step 2: each line of the file is `<executable><TAB><directory>`.
   This is for the script's own tests.
4. Environment for every binary: the current environment, plus `CARGO_MANIFEST_DIR` set to the
   binary's directory, plus every entry of the `[env]` table in `<root>/.cargo/config.toml`, read
   with `tomllib`. An `[env]` value that is not a plain string (cargo also allows a table with
   `value`, `force`, `relative`) is an error that names the key, exit 2: do not guess what cargo
   would do. A missing `.cargo/config.toml` or a missing `[env]` table means no extra entries. If
   `tomllib` cannot be imported, exit 2 saying Python 3.11 or later is needed.
5. Run the binaries `N` at a time (default: the smaller of 4 and the CPU count; `--jobs` must be at
   least 1), each with its directory as the working directory and no arguments, capturing output.
   As each finishes print one line: `ok` or `FAILED`, the binary's file name, its seconds, and for
   a passing binary its `test result:` lines. For a failing binary print its whole output.
6. At the end print the number of binaries, the number failed, the total seconds and the names of
   the failed ones. Exit 0 when all passed, 1 when any failed, 2 for a usage or setup error. An
   executable that cannot be started is a failure that names it, not a skip. No binaries found is
   an error (exit 2), not a pass.

`scripts/test-changed.py`: where it runs `cargo test ...` today, run
`<python> scripts/test-parallel.py -- <the same arguments after "cargo test">` instead, and return
its exit code. Its decisions about which packages to test, and what `--print-only` style options
print about that decision, do not change.

`.github/workflows/ci.yml`: the test step becomes
`python3 scripts/test-parallel.py -- --workspace --all-targets`.

No fallbacks: the script never falls back to plain `cargo test`. Not a long job: nothing to resume.

If a test fails only when binaries run side by side, do not edit, weaken or serialise that test in
this task. Name it in the report, with its output.

### Task PS2b: `blyte clean` gives the same reasons as before PS2

**Depends on:** PS2 (dispatch with `--base wip/PS2`). **Siblings:** none running.

**Why.** PS2 made `decide_run_merged` in `crates/blyte-cli/src/clean.rs` drop a run's base
targets when they are the default branch (`.filter(|t| !self.is_default_target(t))`). The same
runs are still removed, but the reason printed changed, which the plan forbids (no user-visible
change). Measured on one fixture, before PS2 and after:

| run | before PS2 | after PS2 |
|---|---|---|
| base `main`, cherry-picked onto an advanced `main` | `merged into main` | `merged` |
| base `main`, squash-merged with its subject in the message | `merged into main` | `merged` |
| base `main`, same content committed under another message | `merged into main` | `merged` |
| base `main`, with a follow-up run based on it, both cherry-picked | `merged into main` | `merged through E2` |

**Files:** `crates/blyte-cli/src/clean.rs`, `crates/blyte-cli/tests/test_clean_git_calls.rs`. No others.

**What to build.**
1. Remove the `is_default_target` filter from `decide_run_merged`, so base targets are checked in
   the same order and with the same reasons as before PS2 (base-branch checks before the
   follow-up rule, `MergedInto(display_name)` when a base target matches). Delete
   `is_default_target` if nothing else uses it.
2. Keep the process count down without the filter: cache the results of
   `is_cherry_merged_into_target` and `is_merge_tree_merged_into_target` in `CleanContext`, keyed
   by `(commit sha, self.target_key(target))`, and call them through the cache everywhere in
   `CleanContext`. `refs/heads/main` and `main` then share one entry, as `ancestor_cache` already
   does. A cache entry is only ever the result git gave for that exact pair; no default value.
3. No fallbacks: nothing is to be skipped, guessed or defaulted to make the count pass. Not a
   long job, so "resumable" does not apply.

# blyte V1: a session you work in

Date: 2026-11-20

## Problem

blyte is the layer under another harness: Claude Code plans and reviews, blyte implements. The
developer therefore sits in a tool blyte does not control, and three things follow.

- **Too much to read.** Each finished agent reports in prose. With four or five agents the
  developer cannot get through it.
- **No view of the system.** The developer sees conversations and diffs, not the system and data
  design that the work is changing, so understanding of the system erodes as it grows.
- **Nothing limits load.** Parallel agents invite more parallel work, more interruptions and more
  hours. Nothing in the tools shows it or holds it back.

V1 makes blyte the tool the developer sits in, built for flow: design as the developer's work,
a live view of the system, a review queue that can be got through, and load that is limited and
measured.

## What the research supports

Gathered 2026-11-19 and 2026-11-20 from web searches. Most of it is surveys and self-report, and
none of it studies a developer running several coding agents over weeks. Items marked (recall)
were not confirmed against a source in this pass.

| Assumption | Verdict | Basis |
|---|---|---|
| A live system and data map helps | Supported | DevEx framework: cognitive load is one of three drivers of developer experience; AI users scored 17% lower on comprehension unless they engaged with the code |
| One review queue, no interruptions | Supported | Interruptions and task switching are the main flow breakers (DevEx framework; Iqbal and Bailey) |
| Fast feedback matters | Supported | DevEx framework: slow feedback makes developers wait or switch tasks |
| Small tasks, design first | Supported | DORA 2025: AI raises throughput but hurts stability and encourages larger changes; plan-based oversight reduced problematic agent actions |
| Supervising agents is the strain | Supported | BCG survey of 1,488 workers: oversight was the most-cited cause of fatigue; gains flatten past three tools |
| Developers can judge their own state | Not supported | METR: tasks took 19% longer with AI while developers believed they were 20% faster |
| A tool can detect "brain fry" | Not supported | No validated detector found |
| Nudges to take a break fix it | Weak | Micro-break meta-analysis: small gains in vigour, none in performance on demanding tasks |
| Mindfulness training reduces stress | Supported | Meta-analysis of 23 workplace trials, g = 0.56 |
| Mindfulness reduces burnout | Unclear | Results conflict; effects fade after about 12 weeks without continued practice |
| A short in-tool exercise is enough | Not supported | A 10-minute study with 52 developers was inconclusive |
| Mindfulness improves design work | Partly | Three experiments with 130 students found better conceptual modelling; studies of working developers were tentative |

Sources are listed at the end.

## Decisions

### 1. blyte is the top-level harness

blyte gains an interactive session in which the developer talks to an orchestrator that plans
with them, dispatches implementers, and reviews results first. It replaces Claude Code for the
plan, dispatch, review loop. It does not try to match Claude Code feature for feature.

The existing engine carries over unchanged: the gate, sandbox, worktrees, dispatch, review checks
and verdicts, comment lint, cost ledger and plan tracking.

### 2. One surface

A single window holds three regions: the conversation, the map and the review queue. It is one
local application with blyte's session server behind it, in a Rust desktop shell. Nothing in V1
requires moving between a terminal and a browser.

The architecture follows the server-and-clients shape (one session, several views of it), not a
fork of an existing tool. The session server speaks the Agent Client Protocol so that editors can
attach; the map and queue need blyte's own extension to it.

### 3. Design is the developer's work surface

The developer and the orchestrator edit the system design and the data design. Agents implement
against them in small tasks. The design is held as data blyte owns, not as agent-written prose.

### 4. A dynamic map

- **Live.** It is built from the code and watches the worktrees, so modules and schemas change on
  screen while runs are in progress.
- **Intended against actual.** The agreed design is one layer and the code as it is now another,
  with differences marked.
- **Tied to the conversation.** Discussing an element focuses the map on it; selecting an element
  scopes the next question or task to it.

### 5. The review queue

Each item is one decision, and the queue shows only what needs the developer's judgement.

- **Grouped by design element.** The unit is a module or schema on the map, holding every result
  that touches it. A group that grows past what can be reviewed well (the evidence puts this at
  200 to 400 changed lines) splits.
- **Clean results collapse to one line.** Gate passed, only the named files changed, no
  deviations: one line with an accept action. Anything the checks flag can never collapse.
- **Exceptions get a card of fixed size.** It states what needs deciding and where it sits on the
  map.
- **The agent's report and the diff are hidden by default**, one action away.
- **Decisions are actions.** Accept, send back with a note, redo, or hold. A note becomes a
  follow-up task that the orchestrator drafts and the developer confirms in one step.
- **No half-reviewed state.** Leaving an item open asks for one line on what happens next;
  returning shows that line first. Nothing is marked overdue.
- **The orchestrator's own replies have a length budget.**
- blyte records how often hidden detail is opened, to show whether the summaries are trusted.

### 6. How the conversation and the queue interact

- **Arrivals never enter the conversation.** A finished run changes a quiet count and nothing
  else.
- **Review is entered on purpose.** One action moves the surface from designing (conversation and
  map) to reviewing (queue and map).
- **Each group has its own short thread**, scoped to its tasks, diffs and map area. It closes
  with the group, so the main thread stays about design.
- **The orchestrator reviews first** and reports what the checks settled as a line.
- **One exception, negotiated.** When a result touches the element in focus on the map and has a
  flagged check, the orchestrator shows one line at the end of its turn offering it now or later.
  It is a rule, not the orchestrator's judgement. blyte records how often "later" is chosen; if
  that is most of the time, the rule tightens.
- **A run that needs input is a queue item** of its own kind.
- **Review feeds the design.** A decision that changes the design updates the intended layer and
  adds one line to the main thread.

### 7. Limits on load

A cap on work in progress, a bounded review queue, a visible end to the session, and
after-hours work shown plainly. In V1 the limits warn; they do not hold back a dispatch.

### 8. Mindfulness

A short, generic, optional practice is offered at three natural boundaries: after dispatching,
before review, and at the end of a session. Before review there is a two-question check-in on
focus and tiredness. Neither is ever an interruption, and blyte makes no claim to detect fatigue.

### 9. Measurement from the first day

The ledger records load (concurrent runs, queue size, session length, after-hours work),
check-ins and review outcomes together, so that within weeks the developer can see whether this
works for them. This is the data the research lacks.

## Not in V1

- Connectors, a skills ecosystem and editor plugins of blyte's own.
- Detection of fatigue.
- A fork of another harness.
- Limits that block work.
- Use by a team. V1 is for one developer, with nothing that prevents more later.

## Open

- **Orchestrator model.** To be chosen by a blind trial of planning quality, as the implementer
  model was. A blyte-owned session calls a model by API key, so the orchestrator is billed per
  token; that cost has not been estimated.
- **What must carry over from Claude Code on the first day.** Assumed: memory and instruction
  files only.

## To verify before planning

- The session-server interface of the tool whose shape this follows, as it is today.
- Whether the Agent Client Protocol can carry dispatch and review events, or needs extending.
- That the map can be built from code for the languages blyte's users work in, starting with
  Rust and Python.
- A Rust desktop shell that fits the bundled-fonts, no-network rule of the current dashboard.

## Order of work

1. **A clickable mock** that replays a week of real blyte runs through the surface, to test the
   queue and its interaction with the conversation before anything is built.
2. The session server and the surface, with the conversation and the review queue.
3. Load limits, check-ins and practice prompts.
4. The map and the design surface.
